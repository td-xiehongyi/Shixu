# Safe local QQ connection configuration

The Settings flow now uses the production Windows runtime receiver: save the `onebot11-text` source/account/timezone/group authorization, save a literal loopback socket address and a locally supplied token, then explicitly connect that source. Saved authorization and credentials do not open a socket. Approved groups' new text notices enter the existing durable message and Calendar pipeline without per-message confirmation. No QQ/NapCat installation, login, real credential or remote network operation was performed to test this change.

Connection records use the existing `source_secrets` table, protected by the same current Windows user's DPAPI adapter and keyed by exact source/adapter/account. They contain a version marker, endpoint length/address and token bytes; no migration or plaintext file is added, and the legacy raw-token API remains unchanged. Calendar snapshots/migration exclude these records; restore clears local credentials and disables restored source authority. SourceConfig and settings DTOs contain no endpoint/token. The four new main-window/local-origin-only commands are `qq_connection_save`, `qq_connection_read`, `qq_connect`, and `qq_disconnect`. Metadata contains only endpoint, credential presence, active status and fixed error code. A disabled source only receives a ciphertext-presence query, with endpoint null; it is never treated as enabled to decrypt credentials. No token-read command exists. Payload bounds are structural rather than a serialization of the secret payload. Tokens accept 1–4096 ASCII graphic bytes; DNS names, external addresses, URL paths, redirects/proxies and port zero are rejected.

One active source is supported. Another connect returns a visible Conflict and keeps the existing connection. Saving credentials and connecting share a nonblocking control gate covering the entire storage/read/connect operation, so save cannot change the record underneath an in-progress connect. Controls use a four-slot bounded queue, a four-second admission deadline and a five-second reply timeout. Socket construction/authentication runs on the receiver thread outside runtime/database locks, with the existing approximately three-second connection bound and cooperative approximately 100 ms read bound. UI IPC work runs in Tauri's spawn_blocking adapter. Cancelled/expired requests cannot later establish a socket; if a newly successful connection cannot deliver its reply, it closes. A cancelled conflicting request does not close another active connection. Stop rejects queued/future requests, disconnects, and joins workers. Controls remain serviceable while the supervisor is suspended, so explicit disconnect is bounded even then.

Saved and current configuration reads canonicalize only group-set order/duplicates, including legacy protected settings, without rewriting historical message proof/binding bytes or configuration epochs. Other identity, capability, timezone and enabled fields retain their strict checks. The receiver checks current configuration epochs before control and receive work. A changed/disabled/restored source stops the old socket and requires an explicit reconnection with the latest authority. Retirement uses an identity-checked transaction on an already bound source, without binding old configuration or pretending a disabled source is enabled. It invalidates recovery epochs for existing historical recovery groups and current groups, preserves unresolved original anchors/cursors/since, and reopens completed proof from the durable live cursor. A gap persistence failure remains visible and propagates after the socket is stopped; no receive authority is granted by this bookkeeping. Pending delivery acknowledgment still uses the existing durable/current-authority verification. On retirement, a committed and still-authorized delivery may be acknowledged. Revoked or uncommitted pending delivery receives no false acknowledgment; the connection records a Conflict and unverified recovery gap, keeps all durable messages/cursors/work, and retires its bounded pending state so it cannot block a future explicit connection or exit. An unchanged active connection continues after lockvault or main-window close; full exit stops it. Restart creates an idle receiver: saved source enablement does not automatically reconnect. There is no automatic reconnect, history/backfill, attachment or business-send support. `transport_supported` remains the legacy conservative false acceptance flag; the explicit connection metadata reports local socket status without claiming G2.

The password input is uncontrolled, never copied into React state, and cleared immediately at submit and again on success/failure/unmount. Owned Uint8Array and numeric IPC arrays are consumed/cleared, including immediately on unmount while a save reply remains pending. A per-request abort signal wipes locally owned IPC arrays; it does not retract a native payload already delivered or cancel an already authorized protected save. These are best-effort measures: JavaScript immutable strings, browser/IPC serialization, native InvokeBody clones and HTTP/header/handshake library-owned copies cannot all be guaranteed zeroized. No secret-bearing Debug/log/error DTO, environment/argv/query/localStorage use or token file is added.

Tests use synthetic tokens, test-only protectors and real local WebSocket sockets through the same protected-save/explicit-connect/WorkerPorts path as production. They cover Calendar persistence after window close/lock, stop, authority change before/after durable commit, concurrent save/connect, conflicting active source, expiry, queued-stop replies, protection failures and backup exclusion. Windows DPAPI/ACL/WebView/tray runtime, Windows full linking, real ordinary-group QQ delivery and the 100-message/8-hour/performance G2 evidence remain blocked. Windows GNU checks prove native Rust cfg/types/lint only. All twelve release gates remain conservatively BLOCKED, and historical N5 original-byte incident Q1 remains OPEN; no original or gold evidence is reconstructed or overwritten.
